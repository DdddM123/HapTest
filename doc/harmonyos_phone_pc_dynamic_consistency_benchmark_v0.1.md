# HarmonyOS 手机—鸿蒙电脑动态一致性测试 Benchmark V0.1

## 1. Benchmark 定义

本 benchmark 面向“同一 HarmonyOS 应用在手机和鸿蒙电脑上的动态表现是否一致”。

一致性不等于两个设备的像素完全相同，而是指在设备差异存在时，应用仍然满足以下要求：

- 核心任务可完成；
- 关键状态、数据和导航结果一致；
- 控件在当前设备上可见、可操作；
- 触摸、鼠标、键盘和触控板等输入方式具有等效结果；
- 窗口、屏幕和系统状态变化后，任务可以连续；
- 不出现明显的崩溃、冻屏、异常空白、遮挡、错位和不可恢复状态。

本版本优先覆盖单应用、手机与鸿蒙电脑两个设备端，后续可以扩展到跨设备流转、平板、折叠电脑和多设备并行。

## 2. 官方文档依据

本 benchmark 的问题分类来自华为开发者文档中的多设备适配和测试要求：

- [HarmonyOS 多设备开发最佳实践](https://developer.huawei.com/consumer/cn/best-practices/multidevice/)：响应式布局、自适应布局、窗口适配、多设备交互和电脑场景。
- [鸿蒙电脑与平板应用适配开发指南](https://developer.huawei.com/consumer/cn/multidevice/pc/adapt)：最大化、还原、拖拽缩放、最小窗口、键鼠交互、右键、悬停、快捷键和触控等效操作。
- [鸿蒙电脑应用开发入门](https://developer.huawei.com/consumer/cn/multidevice/pc/get-started/)：全屏、分屏、自由窗口、悬浮窗、鼠标、触控板、键盘、剪贴板和性能分析。
- [鸿蒙应用多设备通用适配指南](https://developer.huawei.com/consumer/cn/multidevice/adaptive-apps/)：短屏、设备形态响应式布局、横竖屏和全屏切换、软键盘避让、相机连续性。
- [HarmonyOS 应用测试概述](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V2/app-testing-overview-0000001198515507-V2)：兼容性、稳定性、性能、功耗、安全、UX 和流转测试维度。
- [帧率问题分析](https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-zhenlv)：响应时延、滑动流畅度、丢帧和 AppAnalyzer 场景化检测。
- [HiSmartPerf Device 性能使用指导](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/smartperf-guidelines)：FPS、CPU、GPU、RAM、温度和场景化性能采集。

Android 官方文档可作为跨平台研究的补充参考：

- [Window size classes](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes)：以应用当前可用窗口空间，而不是物理设备类型，驱动布局和测试。
- [Adaptive do's and don'ts](https://developer.android.com/develop/adaptive-apps/guides/adaptive-dos-and-donts)：大屏、多窗口、键盘、鼠标、触控板、焦点和多栏布局的检查原则。
- [Large screen app quality](https://developer.android.com/docs/quality-guidelines/archive/adaptive/large-screen-app-quality)：大屏质量分级，以及 Tab、方向键、快捷键、右键、悬停和拖拽用例。
- [Test different screen and window sizes](https://developer.android.com/training/testing/different-screens)：窗口尺寸、配置变化、状态恢复和自动化测试方法。
- [Save UI states](https://developer.android.com/topic/libraries/architecture/saving-states)：配置变化和进程被系统回收后的 UI 状态保存与恢复。
- [Macrobenchmark metrics](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)：启动时间、帧耗时及 P50/P90/P95/P99 等性能统计方法。

这些 Android 规则用于补充测试问题和实验方法，不直接把 Android 的 API、dp 断点或系统行为当作鸿蒙的实现约束。鸿蒙端仍应以华为开发者文档、实际设备和系统版本为准。

## 3. 执行约定

每条用例至少在手机和鸿蒙电脑各执行一次，并记录：应用版本、API 版本、系统版本、设备型号、窗口状态、输入设备、网络状态、执行日志、截图和性能数据。

推荐将每条用例拆成三种测试轨道：

1. **脚本轨道**：使用 Hypium 或其他 UI 自动化脚本执行固定步骤。
2. **探索轨道**：使用 DevEco Testing 应用探索或模型驱动方式执行同一目标。
3. **人工复核轨道**：对视觉、键鼠体验和无法稳定自动化的硬件能力进行确认。

判定时优先比较“任务结果和状态”，其次比较“布局和交互语义”，最后才比较像素差异。电脑端为了利用更大的屏幕采用双栏、侧边导航或更高信息密度，不应直接判定为不一致。

## 4. Benchmark 用例

| 序号 | 问题名称 | 用例 | 解释 |
|---|---|---|---|
| B01 | 设备形态下的核心布局错位 | 在手机和电脑分别冷启动应用，进入同一个核心页面，记录标题、导航、主内容、主要按钮和列表区域的位置；检查是否重叠、截断、贴边、不可见或出现异常留白。 | 多设备适配要求界面随窗口宽高和设备形态变化。这里测试的是“结构和可用性一致”，不是要求手机和电脑采用完全相同的排列。 |
| B02 | 响应式断点切换错误 | 在电脑端依次执行最大化、缩小窗口、恢复窗口；在每个宽度下检查单栏/双栏、底部导航/侧边导航、列表/详情布局是否正确切换；再次恢复到最大化。 | 官方文档要求根据窗口宽度使用响应式布局和断点能力。动态测试应覆盖断点前、断点中和断点后的页面状态。 |
| B03 | 最小窗口内容不可见或不可操作 | 将电脑窗口拖拽到应用支持的最小尺寸，逐个操作登录、搜索、提交、返回和关闭等关键控件；检查关键内容是否可见，必要内容是否可滚动。 | 华为电脑适配指南明确要求在最小窗口尺寸下检查关键内容的可见性和可操作性。 |
| B04 | 全屏、分屏和自由窗口任务中断 | 在电脑端完成一半表单或编辑任务，依次切换全屏、分屏、自由窗口和悬浮窗口，再回到原窗口；检查输入内容、滚动位置、选中项和页面路由是否保留。 | 电脑支持多种窗口模式。窗口状态变化不应导致任务丢失、页面白屏或状态重置。 |
| B05 | 手机横竖屏与电脑窗口变化后的连续性 | 手机进入详情页并旋转横竖屏；电脑端调整窗口宽高；检查当前页面、阅读位置、播放位置、输入内容和弹窗状态是否保持合理。 | 官方适配指南将横竖屏、全屏切换和窗口变化视为需要动态响应的场景。 |
| B06 | 系统区、安全区和沉浸式布局异常 | 在手机状态栏/导航栏可见和隐藏状态下运行；在电脑全屏、分屏和自由窗口下运行；检查标题、按钮、输入框和底部操作区是否被系统区域遮挡。 | 不同设备的安全区、系统栏和窗口沉浸式能力不同。该用例用于发现手机正常、电脑被遮挡或全屏恢复异常。 |
| B07 | 触摸与鼠标点击结果不一致 | 使用手机触摸点击导航、列表项、按钮和弹窗；在电脑使用鼠标左键执行相同操作；比较页面跳转、选中状态、提交结果和错误提示。 | 电脑端支持鼠标左键点击。核心功能应具有输入方式等效性，而不是只在触摸事件链路上可用。 |
| B08 | 触摸滑动与鼠标/触控板滚动不一致 | 在手机上上下滑动长列表、横向滑动内容；在电脑上使用鼠标滚轮和触控板滚动；检查滚动方向、速度、可达范围、懒加载和列表位置。 | 电脑端需要适配鼠标和触控板等输入。还应覆盖悬停位置滚轮滚动，避免内容无法滚动或滚动对象错误。 |
| B09 | 文本输入与焦点导航异常 | 手机点击输入框并使用软键盘输入、删除和提交；电脑使用鼠标聚焦、键盘输入、Tab/Shift+Tab 切换焦点、Enter 提交；检查焦点可见性、光标位置、输入法和提交结果。 | 电脑适配指南要求验证文本输入和焦点导航。键盘事件不能导致控件跳过、重复提交或焦点丢失。 |
| B10 | 右键、悬停和快捷键缺少等效操作 | 对支持编辑、菜单、工具栏或上下文操作的页面，在电脑执行悬停、右键和快捷键；在手机寻找长按、菜单按钮或其他等效入口；比较功能是否可达。 | 官方建议对高频编辑和工具场景增加右键、悬停和快捷键体验，同时为触控提供等效方式。并非所有应用都必须支持这些能力，但核心功能不能因设备输入差异而不可达。 |
| B11 | 返回、退出和窗口关闭语义不一致 | 手机使用系统返回手势/返回键完成“关闭弹窗—返回上一页—退出页面”；电脑使用窗口返回、Esc、页面返回按钮和关闭窗口；检查返回层级和未保存提示。 | 手机和电脑的返回机制不同。该用例检验导航栈、弹窗层级、焦点和窗口关闭是否保持一致的任务语义。 |
| B12 | 页面状态恢复错误 | 在手机和电脑分别完成“打开列表—滚动—进入详情—返回”的流程；将应用切入后台后恢复，再执行相同流程；比较滚动位置、筛选条件、分页和选中项。 | 多设备应用应保持任务连续。状态恢复错误通常只在后台恢复、窗口重建或尺寸变化后出现。 |
| B13 | 登录、表单和提交结果不一致 | 在手机完成登录或表单填写，在电脑重新执行；覆盖空值、非法值、超长文本、密码显示、提交中、失败重试和成功跳转；比较最终业务状态和提示信息。 | 登录、搜索、浏览、编辑和提交被华为电脑适配指南列为需要验证的核心功能。 |
| B14 | 弹窗、权限和系统对话框遮挡 | 在手机和电脑分别触发权限申请、确认弹窗、日期选择、文件选择或错误提示；尝试确认、取消、返回和重新进入；检查按钮可见、焦点正确且对话框可关闭。 | 不同窗口尺寸和输入设备容易造成弹窗超出可视区域、按钮无法点击或取消后状态未恢复。 |
| B15 | 网络异常下的跨设备行为差异 | 在列表加载、搜索、提交和下载过程中切断网络、制造超时，再恢复网络并点击重试；比较手机和电脑的加载态、错误态、重试结果和数据是否重复。 | 这是动态稳定性和功能一致性问题，不应只比较最终页面，还需比较中间状态和恢复路径。 |
| B16 | 文件访问、上传和下载不一致 | 手机选择图片或文件并上传；电脑使用文件选择器上传同一类型文件；再执行下载、打开、取消和重复选择；比较权限提示、文件名、进度、结果和错误处理。 | 鸿蒙电脑有独立的文件访问和大屏使用场景。文件能力是手机与电脑差异较明显、且容易影响核心任务的系统能力。 |
| B17 | 剪贴板读写结果不一致 | 手机复制应用内文本并粘贴到输入框；电脑执行复制、粘贴和跨窗口粘贴；检查中文、长文本、换行、图片或富文本是否按应用能力正确处理。 | 鸿蒙电脑支持剪贴板能力。benchmark 应验证跨输入方式和跨窗口场景下的数据内容、格式和权限行为。 |
| B18 | 通知、深链接和外部入口路由错误 | 从通知、桌面入口或外部链接启动应用；分别在手机和电脑验证冷启动、热启动、已有页面、未登录和已登录状态；检查是否进入正确页面且参数不丢失。 | 外部入口会绕过常规首页路径，是发现设备端路由、生命周期和状态恢复差异的重要动态场景。 |
| B19 | 相机、媒体和方向状态异常 | 在手机和电脑调用相机、图片、音频或视频能力；切换横竖屏、全屏和窗口状态；检查预览方向、比例、播放位置、暂停/恢复和关闭后的页面状态。 | 官方多设备适配指南特别提示相机预览方向、比例、切屏后的流连续性问题。对不支持的硬件能力，应验证清晰的降级提示。 |
| B20 | 数据同步或跨设备接续不一致 | 在手机打开一篇内容、编辑草稿或播放媒体，在电脑执行接续；再在电脑修改并回到手机查看；比较页面、数据、光标/播放位置和冲突提示。 | HarmonyOS 多设备文档强调自由流转、应用接续和跨设备协同。该用例可作为跨端一致性的扩展轨道。 |
| B21 | 冷启动和热启动性能差异 | 在手机和电脑分别执行冷启动、热启动和从外部入口启动，重复多次，记录启动完成时间和首个可操作时间；比较中位数和长尾。 | 官方测试体系将性能列为核心质量维度，电脑端更大的窗口和资源规模可能暴露不同的启动瓶颈。 |
| B22 | 点击响应与页面完成时延不一致 | 对登录、搜索、切换标签、打开详情和提交等操作各执行多次；分别记录点击到反馈、点击到页面可操作和失败提示出现的时间。 | AppAnalyzer 和性能体验建议将点击响应快、点击完成快作为可检测的场景化指标。 |
| B23 | 滑动流畅度和丢帧差异 | 对首页、长列表、图片列表和视频评论区分别执行固定距离滑动；记录 FPS、丢帧、最大连续丢帧、滑动响应和页面完成时间。 | 官方帧率分析文档将滑动响应和滑动流畅度作为性能体检重点。手机和电脑应使用相同内容规模和相同动作预算。 |
| B24 | 长时间运行后的资源和稳定性差异 | 在手机和电脑上循环执行打开列表、搜索、进入详情、返回、切换窗口和滚动，持续 30～60 分钟；记录崩溃、冻屏、内存增长、CPU、温度和恢复能力。 | 官方测试体系包含稳定性、性能和功耗测试。长时间动态运行用于发现资源泄漏、状态累积和设备端特有故障。 |
| B25 | 窗口宽度分段边界错误 | 在手机、电脑全屏和电脑自由窗口中，逐步改变应用可用宽度，重点测试布局切换前后及临界宽度；记录导航形态、列表列数、详情面板和主要按钮的变化。 | Android 将 compact、medium、expanded 等窗口尺寸作为布局和测试分段，并强调窗口尺寸会在应用运行期间动态变化。鸿蒙 benchmark 可采用自己的窗口分段，但应覆盖边界值和边界附近的连续变化。 |
| B26 | 窗口高度不足导致内容截断 | 在电脑横向短窗口、手机横屏和软键盘弹出状态下执行登录、编辑、提交和弹窗确认；检查底部按钮、错误提示、输入光标和滚动区域是否仍可见。 | Android 文档将窗口宽度和高度分开考虑，并特别提示短高度场景。该用例补充只按宽度判断布局而忽略可用高度的问题。 |
| B27 | 按设备类型判断布局错误 | 在同一设备上切换全屏、分屏和自由窗口，使其获得不同的可用窗口尺寸；比较应用是否按窗口空间改变布局，而不是始终使用“手机布局”或“电脑布局”。 | Android 建议以当前应用窗口而非物理设备类型作为自适应依据。这一原则适合迁移到鸿蒙的多窗口和电脑场景。 |
| B28 | 大屏空白过多或内容被拉伸 | 在电脑最大化窗口打开列表、详情和表单；检查文本行宽、按钮宽度、卡片尺寸和信息密度；确认是否合理采用双栏、列表-详情或侧边导航。 | Android 大屏指南建议使用多栏和列表-详情布局，避免把小屏控件简单拉伸到整个大屏。该用例帮助区分“形式不同但合理”和“布局未适配”。 |
| B29 | 大屏弹窗与上下文菜单定位错误 | 在电脑端从列表项、工具栏和输入框触发弹窗、菜单和操作提示；调整窗口位置和大小后再次触发；检查弹窗是否靠近触发对象、没有超出窗口、且不遮住关键操作。 | Android 大屏 UI 指南要求模态窗口保持合适尺寸，并将上下文菜单放在相关元素附近。鸿蒙端可将其作为电脑端 UX 一致性检查。 |
| B30 | 非触摸模式下焦点不可见 | 断开触摸操作，仅使用电脑键盘 Tab、Shift+Tab、方向键和 Enter 遍历页面；检查所有可操作控件是否可聚焦、焦点顺序是否符合任务顺序、焦点样式是否清晰。 | Android 大屏质量指南把外接键盘导航和可见焦点列为大屏质量要求。该用例可以发现鸿蒙电脑端“鼠标能点但键盘无法完成任务”的问题。 |
| B31 | 常用编辑快捷键语义缺失 | 在文本编辑、搜索或表单页面使用 Ctrl/Cmd+C、V、X、A、Z、Shift+Tab 和 Enter；在媒体页面使用空格或方向键控制播放；比较与触摸操作的结果。 | Android 大屏质量指南覆盖选择、剪切、复制、粘贴、撤销、重做和媒体控制。对鸿蒙应用应根据实际支持的快捷键建立等效功能集合。 |
| B32 | 拖拽操作在不同输入设备下不一致 | 在电脑端用鼠标拖拽列表项、图片或文本到应用内目标；在支持多窗口时从其他窗口拖入或拖出；再用触摸或触控板重复；比较拖拽预览、放置结果、取消和失败提示。 | Android 大屏质量指南明确将应用内和应用间拖放作为大屏测试场景，并要求覆盖触摸、鼠标、触控板等输入。 |
| B33 | 输入设备连接变化后任务中断 | 在应用运行过程中连接或断开硬件键盘、鼠标或触控板；继续执行输入、滚动、快捷键和焦点导航；检查页面是否重建、表单数据是否丢失、焦点是否恢复。 | Android 文档将输入设备变化视为可能触发配置变化的事件，并要求应用准备应对频繁配置变化。该场景可补充鸿蒙电脑外设动态接入问题。 |
| B34 | 配置变化后的 UI 状态丢失 | 在手机旋转、电脑调整窗口、切换分屏和断开外设后，检查表单输入、滚动位置、筛选条件、导航位置和展开状态；进一步将应用切后台并模拟进程重启，再验证恢复。 | Android 将配置变化和系统进程回收分别纳入 UI 状态保存问题。鸿蒙 benchmark 可据此区分“窗口变化恢复”和“进程级恢复”两类缺陷。 |
| B35 | 返回手势与横向内容手势冲突 | 在手机边缘执行返回手势，在应用内执行横向分页、图片浏览或侧滑菜单；分别完成返回、取消返回和内容滑动；电脑端用 Esc、返回按钮或窗口返回复现同一任务。 | Android 的预测返回设计强调手势过程中的预览、提交和取消状态。该用例用于发现应用手势与系统返回手势冲突，以及两端返回语义不一致。 |
| B36 | 无障碍和辅助输入下的任务不可达 | 开启系统文字放大、屏幕朗读或辅助输入能力；在手机和电脑完成登录、搜索、列表选择、弹窗确认和返回；检查控件名称、焦点顺序、触达范围和状态反馈。 | Android 大屏质量和 UI 测试资料将可聚焦控件、触摸目标和辅助操作纳入质量要求。鸿蒙端可将其作为跨设备一致性的扩展质量维度。 |

## 4.1 Android 参考形成的实验方法补充

- **窗口矩阵**：不要只按“手机/电脑”分组，至少增加紧凑、中等、宽屏、最大化、最小窗口、短高度和分屏状态。
- **状态矩阵**：冷启动、热启动、后台恢复、窗口重建、外设连接变化和进程重启应分开记录。
- **输入矩阵**：触摸、鼠标、触控板、键盘 Tab/方向键、快捷键、右键和拖拽分别统计。
- **断言矩阵**：行为断言用于判断任务和状态，截图断言用于判断布局，日志和性能轨迹用于判断稳定性与性能。
- **性能统计**：启动和交互至少报告中位数；帧耗时和响应时延建议报告 P50、P90、P95 和 P99，避免只报告平均值。
- **自动化层级**：页面内控件操作使用 UI 自动化；系统栏、通知、权限、文件选择器和窗口管理使用设备级自动化；视觉和硬件能力保留人工复核。

## 5. 初始判定结果

每条用例建议输出以下结果之一：

- **通过**：两端均完成核心任务，状态和错误处理符合预期。
- **设备差异但合理**：布局或交互形式不同，但功能可达、语义一致且符合电脑/手机设计规范。
- **一致性缺陷**：一端可完成、另一端不可完成，或相同操作造成不同业务状态。
- **稳定性缺陷**：崩溃、冻屏、白屏、无法返回、状态丢失或无法恢复。
- **性能缺陷**：一端出现明显超时、卡顿、持续丢帧、内存增长或资源异常。

建议为每个问题额外记录三个量化指标：

~~~
任务一致率 = 两端均成功完成的用例数 / 执行用例总数
状态一致率 = 两端最终状态相同的用例数 / 可比较用例总数
缺陷复现率 = 重复执行后再次出现的缺陷次数 / 缺陷执行次数
~~~

第一轮研究可以从 B01～B15 和 B25～B30 开始，形成“布局 + 窗口 + 输入 + 功能状态”的核心 benchmark；B16～B24、B31～B36 作为系统能力、辅助输入和性能扩展集。这样既能体现手机—电脑差异，又能吸收 Android 大屏研究中较成熟的窗口、输入和状态恢复测试思想。
